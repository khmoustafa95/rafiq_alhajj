# AGENTS.md

## Cursor Cloud specific instructions

This is a **Flutter** app (`rafiq_alhajj`, an Arabic Hajj-companion) with a **Supabase** local backend
(Postgres + Auth + Storage + Edge Functions running in Docker). The primary dev-testable surface in the
cloud VM is the **Flutter web** build (operator + admin console) served by Chrome. Android/iOS surfaces
(pilgrim, field-operator) are not runnable here (no emulator). Standard commands live in
`docs/runbook-ar.md`, `package.json`, and `pubspec.yaml`; only the non-obvious cloud caveats are below.

### Toolchain (already installed in the VM image)
- **Flutter 3.41.9 / Dart 3.11.5** at `/opt/flutter` (added to `PATH` in `~/.bashrc`). `pubspec.yaml`
  needs Dart `^3.11.4`.
- **Docker** (docker-in-docker with `fuse-overlayfs`; Docker 29 has `containerd-snapshotter` disabled in
  `/etc/docker/daemon.json`, iptables set to legacy).
- **Supabase CLI pinned to v2.90.0** — DO NOT upgrade it. Newer CLIs (2.10x) ship a Postgres image whose
  **default privileges for the `postgres` role only grant `Dxtm` (no SELECT/INSERT/UPDATE) to
  `anon`/`authenticated`/`service_role`**. Because every migration relies on Supabase's default table
  grants (they only define RLS policies, never explicit `GRANT ... ON TABLE`), a newer CLI makes ALL
  REST/auth reads fail with `42501 permission denied for table ...` and the app shows
  "تعذر الاتصال بـ Supabase". v2.90.0 grants full CRUD to the API roles and works correctly.

### Starting services (do this at the start of a session; NOT in the update script)
Docker and Supabase are services, so they must be started manually each session:
1. **Docker daemon** (no systemd in the container): `sudo dockerd` in the background (e.g. a tmux session),
   then `sudo chmod 666 /var/run/docker.sock`.
2. **Supabase**: from repo root, `supabase start` then `supabase db reset` (applies all migrations in
   `supabase/migrations/` + `supabase/seed.sql`). Services bind `0.0.0.0`; API at `127.0.0.1:54321`,
   Studio at `54323`.
3. **Demo auth users**: `node scripts/seed-demo-users.mjs` (idempotent; must run AFTER every `db reset`
   because reset wipes `auth.users`). Accounts (password `demo123456`): `admin@demo.local` (admin),
   `operator@demo.local` (operator), `pilgrim@demo.local` … `pilgrim12@demo.local` (pilgrim).

### Running the web app
- `dart_defines.local.json` (gitignored, `SUPABASE_URL=http://127.0.0.1:54321` + the local shared anon
  JWT) is required. If missing, copy `dart_defines.local.example.json` and set `SUPABASE_ANON_KEY` to the
  `ANON_KEY` from `supabase status -o env` (the local default is stable across resets).
- Dev server: `flutter run -d web-server --web-hostname=0.0.0.0 --web-port=8080 --dart-define-from-file=dart_defines.local.json`
  then open `http://localhost:8080` in Chrome. Web entry is the operator login; the admin login is at
  `#/admin/login`.

### Lint / test / build
- Lint: `flutter analyze --fatal-infos` → clean.
- Codegen (committed to the repo, so only needed after changing `@riverpod`/`freezed`/`json_serializable`
  sources): `dart run build_runner build --delete-conflicting-outputs`. l10n is generated by
  `flutter gen-l10n` / `flutter pub get`.
- Tests: `flutter test --dart-define-from-file=dart_defines.local.json`. Note: `test/app_config_test.dart`
  **requires** the `--dart-define-from-file` flag (it asserts `AppConfig.hasSupabase`).
  `test/widget_test.dart` has a **pre-existing** failure — a ~53px `RenderFlex` overflow in the bare
  800×600 test viewport (guest home layout); it is unrelated to environment setup.
